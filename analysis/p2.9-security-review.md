## Security Review Report: Task P2.9 — Create the yoker_basic suite

### Executive Summary

Task P2.9 introduces a test suite with 30 tasks, including LLM-generated
Python code execution, dynamic task generators loaded via YAML `!function`
tags, and suite-local custom scorers. The existing codebase has a
functional but insufficient sandbox for the `code_execution` scorer, and
the `!function` resolution mechanism allows arbitrary module imports
from any installed Python package. The combination of these features
creates a code execution surface that should be addressed before the
suite is used in any multi-user or CI/CD context.

### Critical Findings (CVSS 9.0-10.0)

#### C1: Restricted Builtins Sandbox is Bypassable

**OWASP A05 (Injection) / A06 (Insecure Design)**

The `code_execution` scorer uses `exec()` with a restricted builtins
dictionary:

```python
def run_code(c: str = code, ns: dict = local_ns) -> None:
    exec(c, {"__builtins__": _RESTRICTED_BUILTINS}, ns)
```

This is a well-known weak sandbox pattern. Python's `exec()` with
restricted `__builtins__` is trivially escapable. An LLM can generate
code that escapes the sandbox via multiple vectors:

1. **Class introspection bypass**: Any object in the restricted builtins
   (e.g., `Exception`) provides access to `__class__`, `__subclasses__()`,
   and ultimately to `os`, `subprocess`, or any module:

   ```python
   [].__class__.__base__.__subclasses__()  # access to object hierarchy
   ```

2. **Generator/coroutine escape**: Accessing `__class__` on any allowed
   type (e.g., `int`, `str`) yields `type`, then `__subclasses__()` gives
   access to `os._wrap_close` and similar classes that expose `os` via
   `__init__.__globals__`.

3. **String formatting**: `str.format` is allowed and can be chained to
   access object attributes.

- **Impact**: An LLM generating malicious code (prompt injection from
  test prompts, or an adversarial model) could execute arbitrary system
  commands — file access, network calls, process spawning, data exfiltration.
- **Remediation**: The `exec()` sandbox must be replaced with a real
  isolation mechanism. Options ranked by security strength:
  1. **Subprocess isolation** (recommended): Execute code in a separate
     Python subprocess with `resource.setrlimit()` for CPU/memory limits,
     `os.chroot()` or containers for filesystem isolation, and a hard
     timeout via `subprocess.run(timeout=...)`. This provides OS-level
     isolation.
  2. **Container isolation**: Run `exec()` inside a Docker/container
     sandbox with no network access and a read-only filesystem.
  3. **AST whitelisting**: As a defense-in-depth layer (not standalone),
     parse the code to an AST and reject any `Attribute` nodes accessing
     dunder attributes (`__class__`, `__subclasses__`, `__globals__`,
     `__builtins__`, `__import__`).
- **Reference**: [CWE-250 (Execution with Unnecessary Privileges)](https://cwe.mitre.org/data/definitions/250.html),
  [OWASP A05:2021 — Injection](https://owasp.org/Top10/A05_2021-Injection/)

### High Findings (CVSS 7.0-8.9)

#### H1: `!function` Tag Allows Arbitrary Module Import

**OWASP A05 (Injection) / A06 (Insecure Design)**

The `_resolve_function` in `loader.py` accepts any dotted path and
imports it via `importlib.import_module()`:

```python
def _resolve_function(dotted_path: str) -> Callable:
    parts = dotted_path.rsplit(".", 1)
    module_path, attr_name = parts
    module = importlib.import_module(module_path)
    func = getattr(module, attr_name)
    return func
```

There is no allowlist or path restriction. A YAML suite file can
reference `!function os.system` or `!function subprocess.Popen` or any
installed package's callable. Since the YAML file is trusted (written
by the developer running the test), this is an inherent design choice,
not an external-input vulnerability. However:

1. **If suite files are ever user-supplied** (e.g., shared suites,
   downloaded from the internet), this becomes arbitrary code execution.
2. **Supply chain risk**: A compromised dependency could inject a
   module that shadows a legitimate generator path.

- **Impact**: Arbitrary code execution at suite load time. Any callable
  in any importable module can be invoked with suite-controlled arguments
  via `generator_config`.
- **Remediation**: Add a module path allowlist for `!function` tags.
  Restrict to suite-local modules (e.g., `suites.yoker_basic.generators`)
  and a small set of approved modules. Example:

  ```python
  _ALLOWED_FUNCTION_PREFIXES = (
      "suites.",  # suite-local modules
      "yoker_test.",  # framework modules
  )

  def _resolve_function(dotted_path: str) -> Callable:
      if not dotted_path.startswith(_ALLOWED_FUNCTION_PREFIXES):
          raise ValueError(
              f"!function security: module path {dotted_path!r} is not in "
              f"allowed prefixes: {_ALLOWED_FUNCTION_PREFIXES}"
          )
      # ... existing resolution logic
  ```

- **Reference**: [CWE-829 (Inclusion of Functionality from Untrusted Control Sphere)](https://cwe.mitre.org/data/definitions/829.html)

#### H2: No Resource Limits on `exec()` — Denial of Service

**OWASP A06 (Insecure Design)**

The `code_execution` scorer has a timeout (default 5s, configurable) but
no memory or CPU resource limits. LLM-generated code can:

1. Allocate unbounded memory: `x = [0] * 10**9`
2. Create infinite recursion (the timeout catches this, but only after
   consuming stack/CPU)
3. Fork bombs via class introspection escape (see C1)
4. Create large data structures that persist between test cases

The `ThreadPoolExecutor` timeout catches wall-clock time, but does not
limit memory. A single malicious or buggy LLM response can consume all
available memory, crashing the evaluation process.

- **Impact**: Denial of service — evaluation process crash, OOM kills,
  resource exhaustion on the host.
- **Remediation**: Add `resource.setrlimit(resource.RLIMIT_AS, ...)`
  before `exec()` to cap memory. Use subprocess isolation (see C1) which
  allows separate resource limits per execution. Also consider
  `RLIMIT_NPROC` to prevent process forking.

### Medium Findings (CVSS 4.0-6.9)

#### M1: Suite-Local Scorers Loaded Without Registry Validation

**OWASP A06 (Insecure Design)**

The TODO spec calls for `suites/yoker_basic/scorers.py` with custom
scorers (`count_bullet_lines`, `tool_call_verify`). The current
architecture resolves scorers in two ways:
1. String name → looked up in the built-in `SCORERS` dict
2. Callable → used directly (set via `!function` tag)

For suite-local scorers, the YAML would reference them via
`!function suites.yoker_basic.scorers.count_bullet_lines`. This means
`suites/yoker_basic/` must be importable as a Python package (requires
`__init__.py` or sys.path manipulation). The current `loader.py` does
not add the suite directory to `sys.path`, so this will either:

1. **Fail silently** (module not found) — a usability issue, not security.
2. **Require sys.path modification** — which would be a new attack
   surface if suite directories are user-controlled.

Additionally, the runner (`runner.py`) only looks up scorers by name
in the global `SCORERS` dict:

```python
if callable(task.scorer):
    scorer = task.scorer
else:
    scorer = SCORERS[task.scorer]
```

Custom suite-local scorers referenced by string name (not `!function`)
would fail with a `KeyError`. The spec doesn't clarify whether
suite-local scorers should be auto-registered into `SCORERS` or
always referenced via `!function`.

- **Impact**: Functional gap that could lead to insecure workarounds
  (e.g., dynamically injecting into `sys.path` or monkey-patching the
  `SCORERS` dict).
- **Remediation**: Define an explicit, documented mechanism for
  suite-local scorer loading. Recommended approach:
  1. After `load_suite()` parses the YAML, check for a `scorers.py`
     in the suite directory.
  2. If present, import it and register any functions decorated with
     `@scorer` (or matching a naming convention) into a suite-local
     scorer registry.
  3. Do NOT modify the global `SCORERS` dict — use a per-suite dict
     that the runner is aware of.
  4. Do NOT add the suite directory to `sys.path` globally — use
     `importlib.util.spec_from_file_location()` for a scoped import.

#### M2: `generator_config` Passed Directly to Generator Functions

**OWASP A05 (Injection)**

The loader passes `generator_config` (arbitrary YAML data) directly
to the resolved generator function:

```python
config = generator_config or {}
generated = task_generator(config)
```

If a generator function uses this config unsafely (e.g., passing it to
`eval()`, `exec()`, or as a format string), it creates an injection
vector. The framework cannot prevent this, but it should document the
contract: generator functions must treat `generator_config` as
untrusted data.

- **Impact**: Potential injection if generator functions are
  written carelessly. Low likelihood for the initial yoker_basic
  suite (generators will be simple math problem generators), but the
  pattern sets a precedent.
- **Remediation**: Document in the suite authoring guide that
  `generator_config` is arbitrary data and generator functions must
  validate/sanitize it. Consider adding a type annotation or
  validation step in `load_suite()` that restricts `generator_config`
  to primitive types (str, int, float, list, dict).

#### M3: No Input Validation on Suite YAML Structure

**OWASP A06 (Insecure Design)**

`load_suite()` performs minimal validation on the parsed YAML. It
checks for required top-level fields but does not validate:
- `scorer_config` values (could contain arbitrary data passed to scorers)
- `test_cases` structure in `code_execution` (args could be any type)
- `expected` field (could be any YAML-serializable type)
- `prompt` field (no length limit, no content validation)

The `validate_suite()` function checks structural completeness but
not content safety. A malicious suite file could include extremely
long prompts (memory exhaustion), deeply nested structures (parser
bombs), or unexpected types in scorer configs.

- **Impact**: Low for trusted suites, but relevant if suites are ever
  shared or user-supplied.
- **Remediation**: Add content validation to `validate_suite()`:
  - Cap `prompt` length (e.g., 10,000 chars)
  - Cap `scorer_config` nesting depth
  - Validate `test_cases` args are primitives or lists of primitives
  - Validate `expected` is a string, number, or None

### Low Findings (CVSS 0.1-3.9)

#### L1: Error Messages May Leak System Information

**OWASP A09 (Security Logging Failures) / A10 (Exception Handling)**

The `code_execution` scorer catches all exceptions and scores 0.0,
which is correct. However, the `_resolve_function` error messages
include the original `ImportError` message, which may leak system
path information:

```python
raise ValueError(f"!function could not import module {module_path!r}: {e}")
```

- **Impact**: Minor information disclosure — module paths, system
  structure visible in error output.
- **Remediation**: Sanitize error messages to not include the original
  exception details in user-facing output. Log full errors internally.

#### L2: ThreadPoolExecutor Created Per Test Case

**OWASP A06 (Insecure Design)**

In `code_execution`, a new `ThreadPoolExecutor` is created for every
test case:

```python
with ThreadPoolExecutor(max_workers=1) as executor:
    future = executor.submit(run_code)
    future.result(timeout=timeout)
```

This is functionally correct but creates and tears down a thread pool
for each case. While not a security issue per se, it means the timeout
is per-case, not per-task. An LLM response with code that consumes
`timeout * len(test_cases)` total wall-clock time could cause
unexpected delays.

- **Impact**: Minor — unexpected evaluation duration.
- **Remediation**: Use a single executor per task or add a total
  timeout for all test cases combined. This is a reliability concern
  more than security.

### STRIDE Threat Model: yoker_basic Suite Execution

#### Trust Boundaries

```
[Suite YAML File] → [Loader/Parser] → [SuiteConfig] → [Runner] → [Yoker Agent] → [LLM Response] → [Scorer] → [TestResult]
     |                   |                                                            |
     v                   v                                                            v
[!function resolve]  [exec() sandbox]                                           [code_execution: exec()]
[generators.py]      [validate_suite()]                                          [LLM-generated code]
[scorers.py]
```

Trust boundary 1: Suite YAML → Framework (developer-controlled, trusted)
Trust boundary 2: LLM response → Scorer (untrusted, model-generated)

#### Spoofing
- **Threat**: LLM could impersonate a different model's output format.
- **Mitigation**: Model identity is set by the runner, not the response. Not applicable.

#### Tampering
- **Threat**: LLM-generated code tampers with test results or suite state.
- **Mitigation**: `exec()` sandbox (currently insufficient — see C1).
  Scorer operates on response string only; no write access to suite state.

#### Repudiation
- **Threat**: Test execution cannot be traced back to specific model/version.
- **Mitigation**: `RunMetadata` captures model, yoker_version, timestamp. Adequate.

#### Information Disclosure
- **Threat**: LLM-generated code reads files from the host filesystem.
- **Mitigation**: Restricted builtins prevents `open()` directly, but
  class introspection bypass (C1) makes this exploitable. **Critical gap.**

#### Denial of Service
- **Threat**: LLM-generated code consumes all memory or CPU.
- **Mitigation**: Timeout exists (5s default) but no memory limits (H2).
  **High gap.**

#### Elevation of Privilege
- **Threat**: LLM-generated code escapes sandbox and runs as the host user.
- **Mitigation**: Restricted builtins (bypassable — C1). **Critical gap.**

### Blocking/Related Findings — Detailed Remediation

#### C1: Sandbox Bypass — Recommended Fix

Replace the current `exec()` approach with subprocess isolation. The
`code_execution` scorer should:

1. Write the LLM-generated code to a temporary file.
2. Spawn a Python subprocess with:
   - `resource.setrlimit(RLIMIT_AS, max_memory)`
   - `resource.setrlimit(RLIMIT_CPU, max_cpu_seconds)`
   - No network access (if possible, via `--no-network` or namespace
     isolation)
   - A strict timeout via `subprocess.run(timeout=...)`
3. The subprocess imports the code, runs the test case, and prints the
   result as JSON to stdout.
4. The parent process reads stdout and scores accordingly.

This provides OS-level isolation: even if the LLM-generated code escapes
Python-level restrictions, it is confined to the subprocess with
resource limits and no access to the parent process's memory.

**Simpler alternative for immediate use**: Add AST-level validation
that rejects any code containing attribute access to dunder names
(`__class__`, `__subclasses__`, `__globals__`, `__builtins__`,
`__import__`, `__loader__`, `__spec__`). This is defense-in-depth and
NOT a complete fix, but raises the bar significantly:

```python
import ast

_DANGEROUS_DUNDERS = frozenset({
    "__class__", "__subclasses__", "__globals__", "__builtins__",
    "__import__", "__loader__", "__spec__", "__dict__", "__dir__",
    "__bases__", "__mro__",
})

def _validate_code_safety(code: str) -> bool:
    """Reject code that accesses dangerous dunder attributes."""
    try:
        tree = ast.parse(code)
    except SyntaxError:
        return False
    for node in ast.walk(tree):
        if isinstance(node, ast.Attribute):
            if node.attr in _DANGEROUS_DUNDERS:
                return False
    return True
```

This should be added to `code_execution` before the `exec()` call, and
the result should score 0.0 if validation fails.

#### H1: `!function` Allowlist — Recommended Fix

Add a module path prefix allowlist to `_resolve_function()`:

```python
_ALLOWED_FUNCTION_MODULES = (
    "suites.",       # suite-local generators and scorers
    "yoker_test.",   # framework-internal modules
    "math",          # safe standard library
    "random",        # safe standard library (used by generators)
)
```

This prevents `!function os.system` and similar. The allowlist should be
extensible via configuration but have a secure default.

### Positive Observations

1. **YAML SafeLoader**: The loader correctly uses `yaml.SafeLoader` as
   the base class, not `yaml.FullLoader` or `yaml.Loader`. This prevents
   arbitrary Python object deserialization from YAML tags.
2. **Timeout mechanism**: The `ThreadPoolExecutor` with timeout is a
   good practice, even if incomplete. It prevents infinite loops from
   hanging evaluation indefinitely.
3. **Exception handling in runner**: `_execute_once` catches all
   exceptions and converts them to error results, preventing one task
   failure from crashing the entire evaluation.
4. **No network calls in scorers**: The built-in scorers don't make
   network calls. The `code_execution` sandbox doesn't include `requests`
   or `urllib` in the restricted builtins.
5. **Clear separation**: Scorers receive `(TestTask, str)` — the response
   is a string, not a live object. This prevents scorers from accessing
   the agent's internals.
6. **Validate function**: `validate_suite()` provides a structural
   validation layer that catches missing fields, duplicate IDs, and
   unknown scorer names before execution.

### Recommendations (Prioritized)

1. **[Blocking]** Replace `exec()` sandbox with subprocess isolation or
   at minimum add AST validation rejecting dunder access (C1).
2. **[Related]** Add module path allowlist to `!function` resolution (H1).
3. **[Related]** Add `RLIMIT_AS` memory cap to code execution (H2).
4. **[Related]** Define and implement explicit suite-local scorer
   loading mechanism (M1).
5. **[New]** Add `generator_config` validation and document the
   generator function security contract (M2).
6. **[New]** Add YAML content validation (prompt length, nesting depth)
   to `validate_suite()` (M3).
7. **[New]** Sanitize error messages to avoid path disclosure (L1).
