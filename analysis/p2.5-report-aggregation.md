## Summary

This analysis reviews the design for five new functions in `report.py`:
`aggregate_results`, `summarize_overall`, `compare_baseline`,
`format_console_report`, and `format_quality_ranking`. The existing
`compute_composite` and `print_report` remain for backward compatibility.

The schema dataclasses (`CategorySummary`, `OverallSummary`,
`ComparisonReport`, `TestReport`) are already in place from P2.1 and
already have `to_yaml()`, `to_json()`, `to_dict()`. **No schema changes
are needed.** The work is pure logic: compute aggregations from
`list[TestResult]`, populate the existing dataclasses, and format strings.

## Design Decisions

### D1: Standalone Functions, Not Methods

**Decision**: Standalone functions in `report.py`.

**Rationale**: The TODO says "in report.py" and the existing `compute_composite`
and `print_report` are already standalone functions. The functions take
`list[TestResult]` and `dict[str, CategorySummary]` as inputs — they are
transformations, not stateful operations on a `TestReport` instance.
`TestReport` is a data container, not a computation engine.

The functions could later be wired as convenience methods on `TestReport`
(e.g., `report.aggregate()`) that delegate to these functions, but the core
logic stays standalone for testability and separation of concerns.

### D2: Plain Text Formatting, Not Rich

**Decision**: Plain text string formatting. No Rich dependency.

**Rationale**:
- The project currently uses `print()` with plain text (see `print_report`).
- `pyproject.toml` does not list `rich` as a dependency. Adding it is a
  scope expansion that should be a separate decision.
- The functions return `str`, not `None` — they are formatters, not printers.
  This makes them testable without `capsys` and allows the caller to decide
  output destination (stdout, file, buffer).
- The existing `print_report` prints directly; the new functions return
  strings. The CLI can `print(format_console_report(report))`.
- A future task can add Rich formatting if desired — the `str`-returning
  API is forward-compatible (wrap with Rich panels, tables, etc.).

### D3: Baseline Loading Is Out of Scope

**Decision**: `compare_baseline` takes two `TestReport` objects. Loading a
baseline `TestReport` from YAML/JSON is handled elsewhere (P2.10 baseline
registry, or a simple `yaml.safe_load` + manual reconstruction in the CLI).

**Rationale**: `compare_baseline` is a pure comparison function. How the
baseline `TestReport` is constructed is a separate concern (I/O, registry
lookup). Keeping this function pure makes it trivially testable: construct
two `TestReport` objects in test code, call `compare_baseline`, assert
deltas and flags.

A helper `load_report(path: str) -> TestReport` could be added to `report.py`
or `loader.py` in a future task if reconstruction from YAML proves
non-trivial (the `to_dict`/`from_dict` asymmetry needs addressing — `to_dict`
uses `asdict` which serializes callables as their repr, and `scorer` on
`TestTask` is `str | Callable`). For now, the comparison function itself
doesn't need it.

### D4: Equal Weighting When Weights Are None

**Decision**: When `weights` is `None`, default to equal weighting across
all categories present in the results.

**Rationale**: This is the simplest sensible default. If there are 5
categories, each gets weight 0.2. The alternative (unweighted mean of all
results regardless of category) would be biased by categories with more
tasks. Equal category weighting treats each category as equally
important, which is the neutral default.

When `weights` is provided, categories not in the weights dict are
excluded from the weighted average (their weight is 0). Weights are
normalized to sum to 1.0 before computing the weighted mean.

### D5: Quality Ranking Uses `RunMetadata.model` for Model Names

**Decision**: `format_quality_ranking(reports: list[TestReport])` extracts
model names from `report.run.model`.

**Rationale**: `RunMetadata.model` is always populated by `EvalRunner.run()`.
No additional parameter is needed. The function sorts by
`report.overall.score` (descending) and formats a table with model, quality
score, and usage delta (if available).

If `report.overall` is `None` (un-aggregated report), the function should
skip that report or raise a clear error. I recommend raising
`ValueError` with a message like "Report for model '{model}' has no
overall summary — call summarize_overall first."

## Function Specifications

### 1. `aggregate_results`

```python
def aggregate_results(
  results: list[TestResult],
  weights: dict[str, float] | None = None,
) -> dict[str, CategorySummary]:
```

**Algorithm**:

1. Group `results` by `category`.
2. For each category:
   - `scores = [r.score for r in cat_results]`
   - `score = mean(scores)`
   - `std = stdev(scores)` if len > 1, else 0.0
   - `n_tasks = len(cat_results)`
   - `avg_tokens_in = mean(r.tokens_in or 0 for r in cat_results)`
   - `avg_tokens_out = mean(r.tokens_out or 0 for r in cat_results)`
   - `avg_latency_ms = mean(r.latency_ms for r in cat_results)`
   - `total_tokens = sum(r.tokens_in or 0 + r.tokens_out or 0 for r in cat_results)`
   - `total_latency_s = sum(r.latency_ms for r in cat_results) / 1000.0`
3. Return `dict[str, CategorySummary]`.

**Note on `n_tasks`**: This is the number of `TestResult` entries, which
includes repeats. A suite with 8 tasks × 3 repeats = 24 results for that
category. `n_tasks` = 24. This is correct — the std is computed over all
individual results (including repeats), which gives the actual variance
of the model's performance.

**Note on `weights`**: The `weights` parameter is accepted here for API
symmetry but is **not used** in `aggregate_results`. Weighting is applied
at the overall level in `summarize_overall`. The parameter is kept to
match the TODO spec signature. It can be ignored or used for future
per-category weight-aware aggregation. I recommend keeping it in the
signature but not using it, with a docstring note.

Actually, re-reading the TODO: the signature is
`aggregate_results(results: list[TestResult], weights: dict[str, float] | None)`.
The weights are for `summarize_overall`. Passing them to
`aggregate_results` seems like a design error in the TODO. I recommend
dropping `weights` from `aggregate_results` — it's not needed there.
The function computes per-category stats; weighting is an overall-level
concern.

**Revised signature**:
```python
def aggregate_results(
  results: list[TestResult],
) -> dict[str, CategorySummary]:
```

**Edge cases**:
- Empty results list → empty dict.
- Single result per category → std = 0.0.
- `tokens_in`/`tokens_out` are `None` → treat as 0.
- All scores identical → std = 0.0.

### 2. `summarize_overall`

```python
def summarize_overall(
  results: list[TestResult],
  category_summaries: dict[str, CategorySummary],
  weights: dict[str, float] | None = None,
  usage_delta: dict[str, float] | None = None,
) -> OverallSummary:
```

**Algorithm**:

1. Determine weights:
   - If `weights` is `None`: equal weighting — `w = 1.0 / len(categories)`.
   - If `weights` is provided: use provided weights, normalized to sum 1.0.
     Categories not in weights dict get weight 0.
2. Compute weighted score:
   - `score = sum(cat_sum.score * w[cat] for cat in categories)`
3. Compute weighted std (propagation of uncertainty):
   - `std = sqrt(sum((cat_sum.std * w[cat])^2 for cat in categories))`
   - This is the standard formula for the uncertainty of a weighted sum
     of independent random variables.
4. Compute totals:
   - `total_tokens_in = sum(r.tokens_in or 0 for r in results)`
   - `total_tokens_out = sum(r.tokens_out or 0 for r in results)`
   - `total_tokens = total_tokens_in + total_tokens_out`
   - `total_latency_s = sum(r.latency_ms for r in results) / 1000.0`
5. Compute throughput:
   - `avg_tokens_per_second = total_tokens_out / total_latency_s`
     if `total_latency_s > 0`, else 0.0
   - Using `total_tokens_out` (not `total_tokens`) because throughput
     measures output generation speed, not input processing.
6. Assemble `OverallSummary` with `usage_delta` passed through.

**Weight normalization**:
```python
if weights is None:
  w = {cat: 1.0 / len(categories) for cat in categories}
else:
  total = sum(weights.get(cat, 0.0) for cat in categories)
  if total > 0:
    w = {cat: weights.get(cat, 0.0) / total for cat in categories}
  else:
    w = {cat: 1.0 / len(categories) for cat in categories}
```

**Edge cases**:
- Empty results → score=0.0, std=0.0, all totals=0.
- `usage_delta` is `None` → `OverallSummary.usage_delta = None`.
- `total_latency_s` is 0 → `avg_tokens_per_second = 0.0`.
- Category in `category_summaries` but not in `weights` → weight 0,
  excluded from weighted mean.
- Category in `weights` but not in `category_summaries` → ignored
  (no results to weight).

### 3. `compare_baseline`

```python
def compare_baseline(
  current: TestReport,
  baseline: TestReport,
) -> ComparisonReport:
```

**Algorithm**:

1. Build delta dict:
   - For each category in `current.summary`:
     - `delta[cat] = current.summary[cat].score - baseline.summary[cat].score`
     - (if category exists in baseline; skip if not)
   - `delta["overall"] = current.overall.score - baseline.overall.score`
     (if both have `overall`)
2. Flag regressions:
   - For each category: if `abs(delta[cat]) > 2 * current.summary[cat].std`
     and `std > 0`, flag it.
   - For overall: if `abs(delta["overall"]) > 2 * current.overall.std`
     and `std > 0`, flag "overall".
   - Only flag negative deltas as regressions? No — the TODO says
     "flag where |delta| > 2 × std", which catches both regressions
     and improvements. Both are interesting signals. Flag both, but
     the sign of the delta indicates direction.
3. Assemble `ComparisonReport` with `baseline=baseline.run`.

**Edge cases**:
- `baseline.summary` is empty → all deltas are 0.0, nothing flagged.
- `current.overall` or `baseline.overall` is `None` → skip overall delta.
- Category exists in current but not baseline → delta = current score
  (new category), no flagging (no baseline std to compare against).
- Category exists in baseline but not current → skip (category removed).
- `std == 0` → never flag (avoid division issues; with std=0 any non-zero
  delta would be flagged, which is noisy). The condition `abs(delta) > 2*std`
  with `std=0` means `abs(delta) > 0` — any delta is flagged. This is
  actually correct: if there's zero variance and the score changed, that's
  a real signal. I recommend keeping this behavior.

### 4. `format_console_report`

```python
def format_console_report(
  report: TestReport,
) -> str:
```

**Algorithm**:

The function builds a multi-section string:

1. **Header**: suite name, model, provider, yoker version, timestamp.
2. **Per-task detail**: for each result, compact one-line summary:
   `  K1  knowledge  easy  r0  score=1.0  tokens=15  latency=42ms`
   Group by category. Show error indicator if `result.error` is not None.
3. **Category summaries**: table format:
   ```
   Category      Score   Std    N   Avg In   Avg Out  Avg Lat   Total Tok
   knowledge     0.875   0.00   24  40       4        900ms     1080
   reasoning     0.625   0.05   24  65       120      2800ms    7800
   ```
4. **Overall summary**: score, std, total tokens, total latency,
   tokens/sec, usage delta (if available).
5. **Comparison** (if `report.comparison` is not None): delta table with
   flags marked.

**Formatting**: Plain text with fixed-width columns. Use f-string
formatting with consistent widths. No external formatting library.

**Edge cases**:
- `report.summary` is empty → note "No category summaries available."
- `report.overall` is `None` → skip overall section.
- `report.comparison` is `None` → skip comparison section.
- `report.results` is empty → note "No results."

### 5. `format_quality_ranking`

```python
def format_quality_ranking(
  reports: list[TestReport],
) -> str:
```

**Algorithm**:

1. Filter: skip reports where `report.overall` is `None`.
   Raise `ValueError` if all reports lack overall summaries.
2. Sort by `report.overall.score` descending.
3. Format table:
   ```
   Rank  Model                Quality   Std    Tokens   Latency    Usage Δ
   1     gpt-4o               0.900     0.02   12000    45.0s      0.15%
   2     llama3.1:8b          0.570     0.03   8000     30.0s      0.00%
   3     llama3.2:3b          0.400     0.04   6000     20.0s      0.00%
   ```
4. Usage delta: show `session` value from `report.overall.usage_delta`
   if available, else "N/A". Display as percentage with 2 decimal places.
5. Return the formatted string.

**Edge cases**:
- Empty `reports` list → return "No reports to rank."
- Single report → still show a table with rank 1.
- Reports with no `overall` → raise `ValueError` listing which models
  are missing summaries.
- Tie scores → stable sort, same rank number? No — use sequential
  numbering. Ties are broken by model name (alphabetical) for
  deterministic output.

## Interaction with Existing Schema

```
list[TestResult]
       │
       ▼
 aggregate_results ──► dict[str, CategorySummary]
       │                         │
       ▼                         ▼
 summarize_overall ──► OverallSummary
       │                         │
       ▼                         ▼
  TestReport (summary + overall populated)
       │
       ├──► format_console_report ──► str
       │
       ├──► compare_baseline(current, baseline) ──► ComparisonReport
       │                                                    │
       ▼                                                    ▼
  TestReport (comparison populated)              format_console_report
       │                                         (includes comparison)
       ▼
  format_quality_ranking(reports) ──► str
```

The functions compose cleanly:
```python
# After EvalRunner.run() produces a TestReport with results:
report.summary = aggregate_results(report.results)
report.overall = summarize_overall(
  report.results, report.summary,
  weights=suite_config.aggregation_weights,
  usage_delta=usage_delta,
)
# Optionally compare:
if baseline_report is not None:
  report.comparison = compare_baseline(report, baseline_report)
# Format:
print(format_console_report(report))
# Or rank multiple models:
print(format_quality_ranking([report1, report2, report3]))
```

## Statistical Choices

### Standard Deviation: Population or Sample?

**Decision**: Sample standard deviation (`statistics.stdev`), which uses
N-1 denominator. With 3 repeats per task, this gives a conservative
(slightly larger) std estimate. For the regression flagging rule
`|delta| > 2 × std`, a larger std is more conservative (fewer false
positives).

For categories with n=1 (single result), std = 0.0 (can't compute
sample std with 1 data point).

### Weighted Std for Overall

The weighted std uses propagation of uncertainty for independent
variables: `σ_weighted = sqrt(Σ(w_i × σ_i)²)`. This is the correct
formula when category scores are independent (which they approximately
are — different tasks in different categories).

An alternative is the weighted standard deviation of the category
means, but that conflates within-category variance with between-category
variance. The propagation formula is cleaner and matches the intended
use: "how uncertain is the overall score, given per-category
uncertainty?"

## Error Handling

| Function | Error Case | Behavior |
|----------|-----------|----------|
| `aggregate_results` | Empty results | Return empty dict |
| `aggregate_results` | `tokens_in`/`tokens_out` is None | Treat as 0 |
| `summarize_overall` | Empty results | Return OverallSummary with zeros |
| `summarize_overall` | Empty category_summaries | Return OverallSummary with zeros |
| `summarize_overall` | Weights sum to 0 | Fall back to equal weighting |
| `compare_baseline` | Missing overall on either side | Skip overall delta |
| `compare_baseline` | Category missing from baseline | Skip that category's delta |
| `format_console_report` | Empty results | Note "No results" |
| `format_console_report` | `overall` is None | Skip overall section |
| `format_quality_ranking` | Empty reports list | Return "No reports to rank" |
| `format_quality_ranking` | Report without `overall` | Raise ValueError |

No function should raise on valid-but-empty inputs. `format_quality_ranking`
is the exception because a ranking without scores is a usage error, not
an edge case — the caller should aggregate first.

## Testing Strategy

Tests should use pure data construction (no mocking of Yoker):

```python
results = [
  TestResult(task_id="K1", category="knowledge", score=1.0, ...),
  TestResult(task_id="K1", category="knowledge", score=0.0, ...),
  TestResult(task_id="R1", category="reasoning", score=1.0, ...),
]

summaries = aggregate_results(results)
assert summaries["knowledge"].score == 0.5
assert summaries["knowledge"].n_tasks == 2

overall = summarize_overall(results, summaries, weights={"knowledge": 0.5, "reasoning": 0.5})
assert 0.74 < overall.score < 0.76  # (0.5*0.5 + 0.5*1.0)
```

Key test cases:
1. `aggregate_results`: correct mean/std, None token handling, single result, empty.
2. `summarize_overall`: weighted vs equal, weight normalization, usage_delta passthrough, zero latency.
3. `compare_baseline`: correct deltas, flagging at 2×std, missing categories, missing overall.
4. `format_console_report`: all sections present, empty report, missing overall/comparison.
5. `format_quality_ranking`: sort order, missing overall raises ValueError, empty list, tie handling.
6. Backward compatibility: existing `compute_composite` and `print_report` tests unchanged.
