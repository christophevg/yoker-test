## Summary

This review examines how the yoker_basic suite should be structured to
work with the existing loader, scorers, and runner infrastructure. It
identifies one critical architecture concern (Python import paths for
suite-local modules) and provides concrete recommendations for the YAML
format, generator functions, and custom scorer integration.

## 1. Suite YAML Structure — How It Works with loader.py

### 1.1 What loader.py Expects

The `load_suite()` function in `loader.py` reads the following top-level
YAML keys:

| Key | Required | Type | Description |
|-----|----------|------|-------------|
| `suite` | ✅ | `str` | Suite name |
| `version` | ✅ | `str` | Suite version (quoted to avoid float coercion) |
| `description` | ✅ | `str` | Human-readable description |
| `repeats` | ❌ | `int` | Default: 3 |
| `temperature` | ❌ | `float` | Default: 0.0 |
| `seed` | ❌ | `int` | Default: 42 |
| `max_tokens` | ❌ | `int` | Default: None |
| `aggregation` | ❌ | `dict` | Contains `weights` sub-key |
| `scorers` | ❌ | `dict` | Per-suite scorer config defaults (keyed by scorer name) |
| `tasks` | ❌ | `list[dict]` | Static task definitions |
| `task_generator` | ❌ | `Callable` | Dynamic task generator (via `!function`) |
| `generator_config` | ❌ | `dict` | Config dict passed to task_generator |

### 1.2 Task Dict Fields (via `_build_task`)

Each task in the `tasks` list is a dict with these fields:

| Field | Required | Type | Description |
|-------|----------|------|-------------|
| `id` | ✅ | `str` | Unique task identifier |
| `category` | ✅ | `str` | Category name (e.g., "knowledge") |
| `prompt` | ✅ | `str` | Prompt text sent to the model |
| `expected` | ✅ | `Any` | Expected answer (scorer-dependent) |
| `scorer` | ✅ | `str` or `Callable` | Scorer name or `!function` reference |
| `difficulty` | ❌ | `str` | "easy", "medium", "hard" (default: "") |
| `system_prompt` | ❌ | `str` | Optional per-task system prompt |
| `scorer_config` | ❌ | `dict` | Per-task scorer config (merged with suite-level defaults) |

### 1.4 Dynamic Tasks via !function

The task spec requires "at least 2 dynamic tasks using `!function` tags."
The loader supports two mechanisms:

**Option A: `task_generator` (suite-level)** — A single generator function
produces all tasks dynamically. This replaces the static `tasks` list
entirely. Not suitable here since we need a mix of static and dynamic
tasks.

**Option B: `!function` in `expected` or `prompt` fields** — The YAML
`!function` tag resolves to a Python callable at load time. When used in
the `expected` field, the callable is stored as the expected value. The
scorer must know to call it.

**Option C (Recommended): `!function` for individual dynamic task fields**
— Use `!function` to generate the `prompt` and/or `expected` values for
specific dynamic tasks. The generator function is called at YAML load
time (not at execution time), producing a concrete value.

**Important**: `!function` resolves to a callable. It does NOT call the
function. If the YAML says `expected: !function module.generate_answer`,
the `expected` field will be set to the function object, not its return
value. The scorer would need to call `task.expected()` to get the actual
value.

**Recommended approach for dynamic tasks**: Use a `task_generator`
function that produces a **supplementary** set of dynamic tasks, then
merge them with static tasks. However, the current loader does not
support mixing `task_generator` with static `tasks` — it's one or the
other (`task_generator` takes precedence).

**Concrete recommendation**: Given the loader's current architecture,
the simplest approach is:

1. **Make all 30 tasks static** in the YAML, with the dynamic tasks
   pre-generated at YAML authoring time (hardcoded random seeds).
2. **Provide generators.py** with generator functions that *could* be
   used via `task_generator`, and document how to use them.
3. **OR**: Use `task_generator` exclusively — the generator function
   produces all 30 tasks (mix of static-like tasks + dynamic random
   ones), and generators.py contains the full generation logic.

**Best fit**: Option 3 — a single `task_generator` function that produces
all 30 tasks. This satisfies the "at least 2 dynamic tasks" requirement
naturally (the generator creates random math problems for 2+ tasks while
returning fixed prompts for the other 28). The static `tasks` list in
the YAML can be kept as documentation/reference, but `task_generator`
takes precedence in the loader.

However, this makes the suite harder to read and maintain. The YAML
becomes a thin shell. **Recommendation: ask the owner.**

**If the owner prefers mixed static + dynamic**: We need to modify
`loader.py` to support both `tasks` and `task_generator` simultaneously
(merge static tasks with generated tasks). This is a small change:

```python
# In load_suite():
static_tasks = [_build_task(t, ...) for t in raw.get("tasks", [])]
if task_generator is not None:
    generated = task_generator(generator_config or {})
    static_tasks.extend(generated)  # merge instead of replace
tasks = static_tasks
```

This would be a P2.9 prerequisite change to loader.py.

## 2. generators.py — Function Exposure for !function Tags

### 2.1 How !function Resolution Works

The `_resolve_function` in `loader.py` uses Python's `importlib`:

```python
def _resolve_function(dotted_path: str) -> Callable:
    parts = dotted_path.rsplit(".", 1)
    module_path, attr_name = parts
    module = importlib.import_module(module_path)
    func = getattr(module, attr_name)
    return func
```

The `!function` tag value is a **dotted Python module path**. For
example:

```yaml
scorer: !function suites.yoker_basic.scorers.count_bullet_lines
```

This resolves to: `importlib.import_module("suites.yoker_basic.scorers")`
then `getattr(module, "count_bullet_lines")`.

### 2.2 The Import Path Problem — CRITICAL

**The `suites/` directory is not a Python package.** There is no
`__init__.py` in `suites/` or `suites/yoker_basic/`. The pyproject.toml
only packages `src/yoker_test`. This means:

- `importlib.import_module("suites.yoker_basic.scorers")` will **fail**
  with `ModuleNotFoundError` unless the CWD is the project root AND
  `suites/` has `__init__.py` files.
- Even with `__init__.py` files, this only works when running from the
  project root directory. It won't work in installed mode.

**This is an architecture concern that must be resolved before P2.9
can work.**

### 2.3 Options to Fix the Import Path

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| **A: Add `__init__.py` files** | Create `suites/__init__.py` and `suites/yoker_basic/__init__.py` | Simple, makes suites importable | Only works from project root; suites not installed; pollutes top-level namespace |
| **B: Use `src/yoker_test/suites/`** | Move suites into the package: `src/yoker_test/suites/yoker_basic/` | Suites installed with the package; importable as `yoker_test.suites.yoker_basic.scorers` | Mixes configuration (suites) with framework code; suites become part of the installed package |
| **C: Use sys.path manipulation** | The loader adds the suite's directory to `sys.path` before resolving `!function` tags | Works from any CWD; suites stay in `suites/` | Fragile; potential name collisions; non-standard |
| **D: Relative import from suite dir** | The loader resolves `!function` relative to the suite YAML's directory | Self-contained suites; works from any CWD | Requires loader modification; non-standard Python import |
| **E: Use simple module names** | `!function scorers.count_bullet_lines` + loader adds suite dir to path | Clean YAML; self-contained suites | Requires loader modification |

**Recommended: Option D/E (hybrid)** — Modify the loader to add the
suite's directory to `sys.path` before resolving `!function` tags. This
makes suite-local modules (`scorers.py`, `generators.py`) importable
by simple name. The YAML would then reference:

```yaml
scorer: !function scorers.count_bullet_lines
# or
scorer: !function generators.math_problem
```

**Loader change required** (small, ~5 lines):

```python
def load_suite(path: str | Path) -> SuiteConfig:
    resolved = Path(path).resolve()
    suite_dir = resolved.parent

    # Add suite directory to sys.path for !function resolution
    import sys
    if str(suite_dir) not in sys.path:
        sys.path.insert(0, str(suite_dir))

    with open(resolved, encoding="utf-8") as f:
        raw = yaml.load(f, Loader=SuiteLoader)
    # ... rest unchanged
```

This is the cleanest approach: suites remain in `suites/`, each suite
directory is self-contained (its `scorers.py` and `generators.py` are
directly importable), and it works from any CWD.

**This is a prerequisite change for P2.9. The owner should confirm.**

## 3. Custom Scorers Integration with SCORERS Registry

### 3.1 How Scorers Are Resolved at Runtime

In `runner.py`, the scorer resolution is:

```python
if callable(task.scorer):
    scorer = task.scorer          # direct callable (from !function)
else:
    scorer = SCORERS[task.scorer]  # string name → registry lookup
```

And `validate_suite()` checks:
```python
if isinstance(task.scorer, str):
    if task.scorer not in SCORERS:
        errors.append(f"Unknown scorer: {task.scorer!r}")
elif not callable(task.scorer):
    errors.append("scorer must be string name or callable")
```

### 3.2 Custom Scorers via !function — No Registry Needed

When `scorer: !function suites.yoker_basic.scorers.count_bullet_lines`,
the loader resolves the `!function` tag to a Python callable. The
`_build_task` function stores this callable directly in
`task.scorer`. At runtime, `runner.py` sees `callable(task.scorer)` is
`True` and uses it directly. **No registry modification needed.**

Similarly, `validate_suite()` sees a callable and passes it through.

### 3.3 Custom Scorer Interface

Custom scorers must follow the same interface as built-in scorers:

```python
ScorerFunc = Callable[[TestTask, str], ScorerResult]
# where ScorerResult = float | Score
```

The scorer receives `(task: TestTask, response: str)` and returns either
a bare `float` (0.0–1.0) or a `Score` dataclass.

### 3.4 scorers.py Module Structure

```python
"""Custom scorers for the yoker_basic suite."""

import re
from yoker_test.schema import Score, TestTask


def count_bullet_lines(task: TestTask, response: str) -> float:
  """Score based on the number of bullet-point lines in the response.

  Expected value (task.expected) is the target count.
  Score = min(actual_count, expected) / expected.
  """
  expected_count = int(task.expected)
  lines = response.strip().split("\n")
  bullet_lines = [l for l in lines if re.match(r"^\s*[-*]\s+", l)]
  actual_count = len(bullet_lines)
  if expected_count == 0:
    return 1.0 if actual_count == 0 else 0.0
  return min(actual_count, expected_count) / expected_count


def tool_call_verify(task: TestTask, response: str) -> Score:
  """Verify that the response contains a valid tool call.

  Expected (task.expected) is a dict with:
    - tool: expected tool name
    - args: expected arguments (or partial match criteria)

  Returns a Score with sub_scores for each check.
  """
  expected = task.expected if isinstance(task.expected, dict) else {}
  expected_tool = expected.get("tool", "")
  expected_args = expected.get("args", [])

  sub_scores = {}

  # Check 1: Tool name appears in response
  tool_found = expected_tool.lower() in response.lower()
  sub_scores["tool_name"] = 1.0 if tool_found else 0.0

  # Check 2: Arguments are present
  args_found = all(str(a).lower() in response.lower() for a in expected_args)
  sub_scores["args_present"] = 1.0 if args_found else 0.0

  # Check 3: Response looks like a tool call (JSON or function-call format)
  looks_like_call = bool(
    re.search(r'\{.*["\'](?:tool|function|name)["\'].*\}', response, re.IGNORECASE)
  )
  sub_scores["format"] = 1.0 if looks_like_call else 0.0

  value = sum(sub_scores.values()) / len(sub_scores) if sub_scores else 0.0
  return Score(
    value=value,
    sub_scores=sub_scores,
    explanation=f"tool={expected_tool}, args={expected_args}",
  )
```

### 3.5 Integration Summary

| Scorer Type | How Referenced | How Resolved | Registry? |
|-------------|----------------|--------------|-----------|
| Built-in (mcq, numeric_match, etc.) | String name in YAML | `SCORERS["mcq"]` | ✅ In `scorers.py` SCORERS dict |
| Custom (count_bullet_lines, tool_call_verify) | `!function` tag in YAML | Loader resolves to callable, stored in `task.scorer` | ❌ Not needed — callable used directly |

**No change to the SCORERS registry is needed.** Custom scorers live in
`suites/yoker_basic/scorers.py` and are referenced via `!function`.

## 4. Architecture Concerns

### 4.1 CRITICAL: Suite Module Import Path (see Section 2.3)

The `suites/` directory is not a Python package. `!function` tags
referencing `suites.yoker_basic.scorers` will fail with
`ModuleNotFoundError`. This must be resolved before P2.9 implementation.

**Recommended fix**: Modify `loader.py` to add the suite directory to
`sys.path` before resolving `!function` tags (~5 lines). Then use simple
module names: `!function scorers.count_bullet_lines`.

### 4.2 CONCERN: Mixed Static + Dynamic Tasks

The current loader does not support both `tasks` and `task_generator`
simultaneously — `task_generator` takes precedence and replaces static
tasks. P2.9 requires 30 tasks with "at least 2 dynamic tasks." Options:

1. **All via task_generator**: One generator produces all 30 tasks. YAML
   becomes a thin shell. Harder to read/maintain.
2. **All static, dynamic pre-generated**: Generate random values at
   authoring time, hardcode results. Simplest, but the "dynamic" aspect
   is lost — tasks are effectively static.
3. **Modify loader to support mixed**: Small change to merge static +
   generated tasks. Most flexible.

**Recommendation**: Option 3 (modify loader) or Option 2 (all static
with generators.py as documentation of how dynamic tasks work). Ask
owner.

### 4.3 CONCERN: max_tokens Not Passed Through

The `SuiteConfig` has `max_tokens: int | None = None`, but the
`EvalRunner` constructor in `runner.py` does not receive or use
`max_tokens`. The `config.py:evaluate()` function creates the
`EvalRunner` without passing `max_tokens`. This means the suite-level
`max_tokens: 4096` will be silently ignored.

**Recommendation**: This is a separate task (P2.x for runner
enhancement), but should be noted. The suite YAML can still include
`max_tokens: 4096` — it will be loaded into `SuiteConfig` but not yet
used at runtime.

### 4.4 MINOR: system_prompt Not Used in run_single_test

The `run_single_test` function in `runner.py` always sets
`system_prompt=None` when creating the agent. If any task defines a
`system_prompt`, it will be ignored. The `EvalRunner.run()` method does
pass `system_prompt=task.system_prompt` in the runner, so this depends
on which code path is used. For the suite, tasks with `system_prompt`
should work when run through `EvalRunner`, but not through
`run_single_test` directly.

### 4.5 MINOR: tool_use Tasks Need Agent with Tools

The `run_single_test` creates an agent with `tools=None`. For tool_use
tasks, the model needs actual tools available to call. The current
runner does not configure tools per-task. This means tool_use tasks
will test whether the *model* attempts to emit tool calls in its text
response, not whether Yoker actually executes tool calls.

**This is actually fine for the suite's purpose**: the scorer
(`tool_call_verify`) checks the response text for tool-call-like
patterns. It doesn't need actual tool execution. The task prompt can
instruct the model to "emit a tool call in JSON format" and the scorer
verifies the format. This is a text-level evaluation, not an
integration-level evaluation.
